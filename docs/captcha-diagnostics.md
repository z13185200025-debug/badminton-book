# 滑块通过后，订单仍提示验证码非法校验

网站有两步验证：滑块位置检查，以及提交订单时的二次校验。滑块返回成功不能证明订单已被接受。HTTP 200 也可能携带业务错误 250。

现有失败日志的滑块检查返回成功，订单随后明确拒绝；以前成功的运行也有约 0.4 秒的挑战等待和约 0.5 秒的校验后提交间隔。因此目前不能认定操作速度是根因，也不能用一次请求快或慢证明学校后台的校验状态。

## 当前 1.4.4 的处理

每次只验证、提交一次；验证或订单拒绝后立即停止，不重新取挑战、不自动回查或重提。成功提交后的订单列表回查和最终确认回查各执行一次，未能确认时提示手动核对。旧版 `maxCaptchaAttempts` 配置不会增加实际尝试次数。

## 1.4.2 的历史处理（自动重试已在 1.4.4 停用）

- 按每个请求绑定挑战与检查响应，防止乱序响应污染诊断。挑战响应延迟解析、刷新新挑战时仍保留原校验的证据。
- 在本地内存中读取网页已经产生的校验内容，比较它是否对应同一次滑块检查。不生成、不替换、不重放验证码证明。确认内容不一致时停止提交；无法识别格式时明确显示无法核验，不标为一致。
- 首次尝试维持原速度。仅在收到明确验证码拒绝、并回查确认没有有效订单后，重新取得验证码恢复一次。恢复时拖动前额外等待 600 ms，检查完成后至少等满 1000 ms 才发出订单。网站原有约 500 ms 等待计入这 1000 ms，避免叠加成 1500 ms。
- 每次下单失败先回查订单。超时、断网或不明确的返回不触发盲目重试。一次恢复仍被拒绝则停止。
- 日志区分请求准备、实际发出、本地等待和接口响应。界面分别展示滑块结果、二次内容比较、校验后提交间隔和订单结果。

恢复等待针对可能的处理时序问题，是有界的缓解措施，不代表已确认或修复学校后台根因。需要后续正常预约的服务端结果验证有效性。

## 隐私与证据边界

挑战令牌、密钥、加密校验串和坐标只作内存比较，不写入新增诊断。运行日志仍可能包含本人订单信息；分享前请脱敏。新增日志能判断客户端内容是否一致，不能读取学校缓存或证明服务器采用何种验证配置。
